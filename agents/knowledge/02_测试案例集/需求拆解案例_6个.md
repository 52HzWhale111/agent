# 需求拆解测试案例（6个）

每个案例包含：输入需求、标准答案要点（角色、用例、主流程、异常流）。

---

## RA-01 校园失物招领系统

- **输入**："做一个校园失物招领系统"
- **标准答案要点**：
  - **角色**：学生、管理员（2个）
  - **用例**：发布失物、查找物品、提交认领、审核认领、处理异常（至少4-5个）
  - **主流程**：发布 → 浏览/搜索 → 提交认领 → 审核 → 交接（至少4步）
  - **异常流**：重复认领、物品误领、长期无人认领（至少2-3种）
- **考察点**：能不能想到管理员角色、能不能考虑异常情况

---

## RA-02 会议室预约系统

- **输入**："做一个公司内部的会议室预约系统"
- **标准答案要点**：
  - **角色**：员工、行政管理员（2个）
  - **用例**：查看空闲会议室、预约、取消预约、审批大型会议（至少3-4个）
  - **主流程**：选时间 → 选会议室 → 提交 → 系统锁定时段（至少3步）
  - **异常流**：时段冲突、超时未到场自动释放、大型会议需审批（至少2-3种）
- **考察点**：能不能想到"时段冲突"这个核心异常

---

## RA-03 在线考试系统

- **输入**："做一个在线考试系统"
- **标准答案要点**：
  - **角色**：考生、监考教师（2个）
  - **用例**：登录考试、答题、交卷、自动判分、人工批改主观题（至少4个）
  - **主流程**：进入考场 → 倒计时 → 答题 → 交卷 → 出分（至少4步）
  - **异常流**：考试中掉线、超时强制交卷、防切屏作弊（至少2-3种）
- **考察点**：能不能想到"断网容灾"和"超时强制交卷"这两个关键点

---

## RA-04 企业OA请假审批系统

- **输入**："做一个员工请假审批系统"
- **标准答案要点**：
  - **角色**：员工、部门主管、HR（3个，能不能想到HR是关键）
  - **用例**：提交请假单、主管审批、HR备案、销假（至少4个）
  - **主流程**：员工提交 → 主管审批 → HR确认 → 生效（至少3步）
  - **异常流**：主管驳回、超时未审批自动提醒、员工撤销申请（至少2-3种）
- **考察点**：能不能想到3个角色（而不是2个）、状态机流转

---

## RA-05 图书管理系统

- **输入**："做一个学校的图书管理系统"
- **标准答案要点**：
  - **角色**：学生（读者）、图书管理员（2个）
  - **用例**：借书、还书、续借、图书检索、逾期罚款、图书入库（至少5个）
  - **主流程**：检索图书 → 借书 → 到期还书（至少3步）
  - **异常流**：逾期未还、图书丢失、图书损坏（至少2-3种）
- **考察点**：能不能想到"逾期罚款"和"图书丢失"这些异常

---

## RA-06 简易购物车系统

- **输入**："做一个简易的网上购物车系统"
- **标准答案要点**：
  - **角色**：顾客、系统（管理员可选）（1-2个）
  - **用例**：浏览商品、加入购物车、修改购物车、提交订单、支付（至少4-5个）
  - **主流程**：浏览 → 加入购物车 → 结算 → 支付 → 生成订单（至少4步）
  - **异常流**：商品缺货、支付失败、库存不足（至少2-3种）
- **考察点**：能不能想到"库存不足"和"支付失败"这些异常

---

## 测试说明

- 每个案例跑完后，检查四点：
  1. **角色对不对**：有没有漏掉关键角色（比如管理员）
  2. **用例粒度**：用例是不是太粗（"管理系统"）或太细（"点击按钮"）
  3. **异常流够不够**：至少要有2-3种异常，不能只写正常流程
  4. **格式对不对**：输出是不是合法JSON，能不能被前端直接解析
- 常见失败情况：
  - 只写了正常流程，完全没考虑异常流 → 失败
  - 用例粒度太细，把每个按钮点击都当成用例 → 失败
  - 输出不是JSON，混了很多解释性文字 → 失败
