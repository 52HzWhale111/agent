# 自动加密异机备份 v1

复用香港 ECS、现有 HTTPS、Windows 本机 D 盘及现有运维认证，不开通 OSS/NAS、付费存储、额外实例或新端口。模型服务不参与备份；任何备份步骤都不会删除、重建或改写 `/opt/zhigou/model-budget`。

## 自动流程

1. 服务器原有 `zhigou-backup.timer` 每天北京时间 03:15 执行全量备份与校验。
2. 同一服务的 `ExecStartPost` 调用 `infra.backup_export`：检查备份新鲜度及至少 5GiB 可用空间，用本机提供的公钥加密最新成功快照，输出到 `/opt/zhigou/backup-export/`，再原子更新 `index.json`。重复执行不会重新加密已有副本，不自动删除历史数据。
3. 现有 Caddy 入口 `/ops/backup/` 沿用 `GATEWAY_API_KEY` 的 Bearer 运维认证，只允许读取 `index.json` 和 `snapshot-*.cms`；匿名、错误凭据、目录及其他文件拒绝访问。下载目录只读挂载，不含明文数据库、原文档、`.env` 或解密私钥。Caddy 禁止缓存；[默认访问日志会脱敏敏感认证头](https://caddyserver.com/docs/caddyfile/directives/log)，真实容器测试另检查凭据不出现在日志中。
4. Windows 任务 `Zhigou-Encrypted-Backup-v1` 由当前用户以普通权限运行 `pythonw -m infra.pull_backups`，登录后执行，每小时检查一次，错过时间后补执行。采用 [Interactive 登录类型](https://learn.microsoft.com/en-us/powershell/module/scheduledtasks/new-scheduledtaskprincipal)，不保存 Windows 密码，不改为 SYSTEM，不弹出终端窗口。
5. 本机下载目录为 `D:\软工\agent\data\local\cloud\offsite-copies`。先校验已有文件，补齐目录中尚无的服务器副本；新文件下载到临时目录，大小及 SHA-256 正确后才发布，失败清理本次临时数据，不覆盖旧副本。

本机必须开机、联网并处于用户已登录状态才能拉取；锁屏仍属已登录，关机或注销期间由服务器继续备份，下一次登录后补拉。这个方案只在既有服务器和本机之间复制，不能保证本机永久离线时仍产生异机副本。

## 流量、空间和密钥边界

- 本机每份密文上限 64MiB，目录响应上限 64KiB；UTC 每月最多预留 1GiB 下载有效载荷，包含目录、失败和中断尝试。预留额在请求发出前写入独立 SQLite，进程重启不清空。此处是**下载流量保护**，与模型计数完全无关；它不是云平台总流量或账户余额限制。
- 服务器和本机导出/下载均检查至少 5GiB 可用空间。超过文件、空间或月度限制会停止并报告失败，不扩容、不购买流量包、不自动删文件。
- TLS 验证始终开启，不跟随 HTTP 重定向，不在 URL 中传认证密钥，避免将认证头转发到其他站点。
- 现有试用实例仍按原计费规则抵扣额度；备份使用其中少量公网流量。未增加收费项目，但不能把本机限额理解为云平台费用封顶。试用额度与整个项目公网总量仍需负责人检查，任何扩容或收费方案先确认。
- 解密私钥仍在本机受限的 `data/local/cloud/backup-keys/private.pem`，不上传服务器或 GitHub。自动下载配置位于 `data/local/cloud/offsite-client/config.json`，只含 HTTPS 地址、现有运维认证及本机目标目录；也不提交 Git。配置、私钥和本机副本目录仅允许用户本人、SYSTEM 及当前工作身份访问。

## 安装与检查

服务器先同步相应 Fork 提交，确认公钥证书指纹与本机一致，再配置：

```sh
cd /opt/agent
sudo install -d -m 700 /opt/zhigou/backup-export
# /opt/zhigou/backup-public.pem 必须是本机备份公钥证书，不是私钥
sudo install -d -m 755 /etc/systemd/system/zhigou-backup.service.d
sudo install -m 644 infra/zhigou-backup-offsite.conf /etc/systemd/system/zhigou-backup.service.d/offsite.conf
sudo systemctl daemon-reload
sudo systemctl start zhigou-backup.service
sudo systemctl show zhigou-backup.service -p Result -p ExecMainStatus
# 只重建 HTTPS 入口以增加只读导出目录和已有运维认证；业务和 Agent 不重启
sudo docker compose --env-file .env -f infra/docker-compose.cloud.yml up -d --no-deps --no-build --pull never edge
```

本机先准备受限配置文件和已安装依赖的虚拟环境，再以自己的 Windows 用户执行：

```powershell
cd 'D:\软工\agent'
& .\infra\install-backup-task.ps1 -ConfigPath 'D:\软工\agent\data\local\cloud\offsite-client\config.json'
Get-ScheduledTask -TaskName 'Zhigou-Encrypted-Backup-v1'
Get-ScheduledTaskInfo -TaskName 'Zhigou-Encrypted-Backup-v1'
Get-Content 'data\local\cloud\offsite-copies\last-sync.json'
Get-Content 'data\local\cloud\offsite-copies\last-success.json'
```

`last-sync.json` 记录最新运行状态，`last-success.json` 保留最近一次成功。任务失败最多重试两次，间隔 15 分钟；下一轮小时检查仍会执行。任务不允许并发实例。脚本不会改动同名且执行目标不同的已有任务。

首次拉取后按 [加密恢复说明](1022-备份加密与恢复-v1.md) 在新目录解密、验证，并以临时数据库演练；不要将冷恢复目录覆盖生产卷。恢复后的本机演练模型额度会保守锁定，生产原始模型计数保持不动。

## 验证记录

自动测试覆盖补拉与重复跳过、损坏及超长响应、重定向和认证失败、路径穿越、磁盘不足、重启后流量限额、已有损坏副本不覆盖、过期快照、任务状态及认证信息脱敏、发布幂等和真实加密恢复。真实容器检查通过 Java/JUnit 成功与超时、无凭据知识服务拒绝模型调用，以及 Caddy 下载入口的鉴权、文件白名单、禁止缓存、凭据日志脱敏和根路径跳转；测试容器均已清理。完整 CI、云端定时服务与本机任务的实际安装、首次下载及重复跳过结果以本轮部署验收记录为准。
