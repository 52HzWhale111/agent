# 全量备份、加密导出与隔离恢复 v1

本轮只使用本机 Python、OpenSSL 和本地临时 PostgreSQL 容器，不调用真实模型，不创建云资源，不购买或启用存储服务。代码同步到 Fork；香港 ECS 的现有部署状态继续以 [香港试运行记录](1022-香港试运行-v1.md) 为准。本说明不表示已经建立服务器之外的生产备份副本。

## 补齐的内容

- `infra/backup.sh` 在发布成功备份前生成 `snapshot.json`，统一检查 PostgreSQL 压缩流、网关 SQLite 与注册上传文件、业务原文档及 SHA-256；失败仍停留在 `.partial-*`，不会发布成功目录。
- 使用 `ZHIGOU_COMPOSE_FILE=infra/docker-compose.cloud.yml` 时，额外复制知识容器 `/budget` 中的试运行计数。预算目录复制失败将中止备份。原完整 Compose 不要求模型计数目录。
- `infra/snapshot.py` 提供 `seal`、`verify`、`health`、`encrypt`、`restore`。加密使用 [OpenSSL CMS](https://docs.openssl.org/3.5/man1/openssl-cms/) 的 AES-256-GCM 与 RSA-OAEP，不新增 Python 依赖，不自行实现密码算法。
- 恢复先验证密文，再检查压缩包路径、文件清单、SHA-256、gzip 完整性和 SQLite；只写入一个此前不存在的目录，不覆盖在线数据库、不切换生产卷。错误私钥、篡改、路径穿越或损坏都不会发布恢复目录。
- **云端限额冷恢复默认锁住全部 8 次名额。** 旧备份无法证明备份之后发生的调用，不能恢复成旧的剩余额度。恢复后的 `model-budget` 仍需管理员设置 UID 10001/权限 700，并在新费用授权后另行决定调用安排；工具本身不解锁。备份原始时间保留，另记录恢复时间。

```powershell
cd 'D:\软工\agent'

& .\.venv\Scripts\python.exe -m pytest backend/tests gateway/tests -q
& .\.venv\Scripts\python.exe -m infra.smoke_postgres --wsl-distro Debian
```

Linux/CI 使用 `python -m pytest backend/tests gateway/tests -q` 和 `python -m infra.smoke_postgres`。需要系统已有受支持的 OpenSSL 和本地 Docker；上述脚本不携带云端配置或模型 Key。恢复演练只删除本次随机命名的临时容器和卷，保留本机忽略目录 `data/local/` 下的检查记录。

专项测试覆盖 14 项：五类内容变化、截断的 PostgreSQL 压缩流与符号链接、完整加密恢复及模型拒绝外发、错误私钥与 GCM 篡改、四类路径穿越、普通无额度目录的部署与空文件目录、过期备份与磁盘不足。真实 PostgreSQL 8 组检查还验证注册登录、上传所有权、UML 两个历史版本、答题幂等与统计，以及数据库重启和加密包恢复后的数据一致性。运行结果以本轮测试记录和对应提交的 CI 为准。

2026-10-22 本机实际结果：完整业务／网关／知识／运维回归 **99 项通过**，真实 PostgreSQL **8 组通过**，临时容器与卷已清理。Shell 语法及原完整、香港云端两套 Compose 配置检查通过。没有在本轮重新调用收费模型或做公网业务验收。

## 生产备份与离线加密导出

以下是管理员操作模板，需在脚本更新到相应提交后使用；**本轮没有在云端执行这些命令**。`SNAPSHOT` 必须替换为实际成功备份目录，不选择 `.partial-*`。已有旧备份缺少 `snapshot.json`，不能据此声称其含有模型计数；应保留旧副本，更新脚本后生成一份新备份。

```sh
cd /opt/agent
sudo env ZHIGOU_COMPOSE_FILE=infra/docker-compose.cloud.yml sh infra/backup.sh
SNAPSHOT=/opt/agent/backups/snapshot-实际时间-实际进程号
python3 -m infra.snapshot verify "$SNAPSHOT"
python3 -m infra.snapshot health "$SNAPSHOT" --max-age-hours 36 --min-free-gib 5
```

`health` 会校验整套备份，检查备份年龄与当前磁盘余量；不合格返回非零。默认 36 小时、5GiB，可按实际情况指定。这里只提供可运行巡检命令，尚未接入外部群通知或每日巡检定时器；已有每日备份定时器保持其原职责。不自动删除历史备份。

在**离线接收机器**生成单独的备份解密密钥，不能复用 SSH 私钥，也不要把私钥上传服务器。私钥及明文数据应放在受限目录，Windows 需另确认目录 ACL；Linux 示例：

```sh
umask 077
mkdir -m 700 backup-keys
openssl req -x509 -newkey rsa:4096 -nodes -days 3650 \
  -subj /CN=Zhigou-offline-backup \
  -keyout backup-keys/private.pem -out backup-keys/public.pem
```

仅将 `public.pem` 提供给备份服务器，核对其 SHA-256 指纹后使用。下列导出不包含 `.env`、API Key 或 SSH 私钥；学生数据仍须按敏感数据保管。公钥证书可用于加密，并不证明备份发送者身份，只从自己的受信部署获取备份。

```sh
umask 077
python3 -m infra.snapshot encrypt "$SNAPSHOT" /opt/agent/backups/本次备份.cms \
  --certificate /root/backup-public.pem
```

导出使用受限临时目录，需额外空间容纳 ZIP 和密文；完成/失败后清理临时文件。输出文件必须不存在，不会覆盖旧包。只把 `.cms` 密文传给离线接收机器；存储位置和传输方式尚未配置，任何收费存储或超额公网传输须先取得用户同意。

## 在新目录恢复，再验证业务

离线接收机器应放有本项目源码及相同版本运行依赖。恢复目标必须不存在，且父目录应受限：

```sh
umask 077
python3 -m infra.snapshot restore /离线位置/本次备份.cms /隔离位置/recovered-01 \
  --key /离线位置/backup-keys/private.pem
python3 -m infra.snapshot verify /隔离位置/recovered-01
python3 -m infra.gateway_backup restore /隔离位置/recovered-01/gateway /隔离位置/gateway-01
```

最后一步按新路径修正排队 ZIP 任务中的 `archive_path`；不能直接把快照中的 SQLite 当作已完成路径迁移的运行数据。PostgreSQL 从恢复目录的 `postgres.sql.gz` 导入**空演练数据库**，业务原文档使用同份恢复包中的 `backend-uploads`；具体步骤见 [原部署恢复说明](deploy.md)。正式切换前停止写入、保留旧卷，并验证登录、文件所有权、UML 历史版本、学习统计和网关任务。数据库与网关分别取快照，不承诺跨库同一时刻的事务。
