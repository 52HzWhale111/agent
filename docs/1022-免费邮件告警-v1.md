# v1 服务故障与备份失败邮件告警

沿用现有香港 ECS、Windows 本机和已有 QQ 邮箱 SMTP，不购买短信、云监控套餐、邮件产品或新机器。SMTP 使用 `smtp.qq.com:465`、TLS 证书验证及邮箱授权码；没有模型调用，也不读取或重置模型额度。

## 检测范围

| 事件名 | 检测与通知 |
| --- | --- |
| gateway / backend / knowledge / sandbox | 服务器每轮间隔 30 秒探测 HTTP；单个请求最多 5 秒。故障及恢复通知。知识服务只探测健康接口；沙箱只发 OPTIONS，不调用模型或运行学生代码。 |
| daily-backup | systemd `ExecStopPost` 读取整个服务的 `SERVICE_RESULT`，包含备份主命令与后续加密导出失败；下一次成功时通知恢复。 |
| backup-freshness | 服务器检查已发布密文索引；缺失、时间超过 36 小时／在未来、或备份磁盘空闲不足 5 GiB 时告警。 |
| offsite-backup | 现有 Windows 每小时／登录拉取任务失败时通知；下次拉取成功通知恢复。涵盖公网入口不可达、鉴权失败、密文损坏、索引过期、空间及下载额度不足。 |

邮件只包含事件名、状态和发生时间（UTC），没有请求内容、文档、学生信息或密钥。首次正常运行保持安静，同一故障不会每轮重复排队。故障与恢复事件按发生顺序写入 SQLite；SMTP 故障时保留队列，后续监控重试，每个发送端最多每分钟尝试一封。重启进程保留状态。SMTP 已接受后至本地确认前若进程意外退出，极少数情况下可能重复一封；不能把 SMTP 接受等同于最终进收件箱。

## 私密配置

本机配置在 `data/local/alerts/smtp.json`（已被忽略），字段如下，真实地址和授权码不提交 Git：

```json
{
  "host": "smtp.qq.com",
  "port": 465,
  "username": "你的发件地址@qq.com",
  "password": "QQ邮箱生成的SMTP授权码",
  "to": "你的收件地址@qq.com"
}
```

在 QQ 邮箱设置的账号／账号与安全中开启 SMTP，生成授权码；不要填 QQ 登录密码。Windows 目录仅实际用户、受限执行账号及 SYSTEM 可读。香港服务器保存为 `/opt/zhigou/alerts/config.json`，目录 700、文件 600，只有 root 与运行监控的容器可访问。部署使用服务器临时 RSA 公钥加密配置后传送，在服务器解密；不把授权码粘贴进云助手脚本、仓库或日志。服务器不保存本机备份解密私钥。

单封测试（会向 `to` 发送邮件）：

```powershell
.\.venv\Scripts\python.exe -m infra.alerts --test --config data/local/alerts/smtp.json
```

服务器 Compose 监控读取 `/alerts/config.json`，状态持久化到 `/opt/zhigou/alerts/state/outbox.sqlite3`。通用 Compose 则把 `ALERT_DATA_DIR` 指向的私密目录挂载为 `/alerts`，其中 SMTP 文件也命名为 `config.json`；本轮 Windows 拉取任务单独使用上述 `smtp.json`。没有配置时保留事件并记录 `alert_delivery_failed`，不会宣称通知已送达。旧版通用 JSON Webhook 仍可在 SMTP 文件不存在时通过 `ALERT_WEBHOOK_URL` 使用。

## 安装与检查

云端使用 `infra/docker-compose.cloud.yml`，仅更新监控容器即可加载新模块和挂载。已有每日备份服务再添加告警 drop-in，保留原来的云端备份和加密导出配置：

```sh
sudo install -m 644 infra/zhigou-backup-alerts.conf /etc/systemd/system/zhigou-backup.service.d/alerts.conf
sudo systemd-analyze verify /etc/systemd/system/zhigou-backup.service /etc/systemd/system/zhigou-backup.timer
sudo systemctl daemon-reload
docker compose --env-file .env -f infra/docker-compose.cloud.yml up -d --no-deps --no-build --pull never monitor
docker compose --env-file .env -f infra/docker-compose.cloud.yml exec -T monitor python -m infra.monitor --once
sudo systemctl start zhigou-backup.service
sudo systemctl show zhigou-backup.service -p Result -p ExecMainStatus
```

告警命令以 systemd 的 `-` 前缀运行；邮件网络故障不会改变备份本身的成功／失败结果。重试由运行中的监控容器处理，主业务没有新增凭证或新端口。

在本机既有 `data/local/cloud/offsite-client/config.json` 增加 `alert_config`，值为 SMTP 文件的本机绝对路径；原来的下载 token、目的目录、下载额度数据库及 Windows 任务保持原值。下次既有任务运行即可生效；本机发送队列位于备份目的目录的 `alerts/outbox.sqlite3`。

测试覆盖 SMTP TLS 参数、授权失败脱敏、地址注入拒绝、事件持久化、重复故障去重、投递重试、故障先于恢复、备份 hook 的非零结果与过期／空间检查。上线演练用独立 `backup-drill` systemd 单元模拟加密步骤失败与恢复，不停止线上 Agent；实际每日备份另行完整试跑。

## 运行边界与费用

邮件通过已有邮箱发送，不订购收费告警服务；少量网络字节仍属于现有 ECS 流量，受现有试用额度和邮箱自身限制约束，不能承诺云服务永久免费。不要开通付费短信、DirectMail 或升级套餐。

服务器完全关机、Docker／监控容器整体停止时，同机监控不能主动发信。已登录且联网的本机可在下次每小时拉取时发现公网或备份异常；本机关机／退出登录／断网时不能承担异机探测，恢复后补拉并投递已记录事件。尚未发生且未被任何运行中的探测器观察到的短暂故障无法补报。本机任务的 SMTP 重试随既有计划（每小时，失败任务另有两次 15 分钟重试）进行。

参考：[Python SMTP_SSL](https://docs.python.org/3.12/library/smtplib.html)、[systemd SERVICE_RESULT](https://www.freedesktop.org/software/systemd/man/258/systemd.exec.html)、[阿里云 ECS 常用端口](https://help.aliyun.com/zh/ecs/user-guide/common-ports)。
